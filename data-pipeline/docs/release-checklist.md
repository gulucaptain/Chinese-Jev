# 发布与验收

## 自动结构验收

`build` 完成后自动调用 `verify`，检查生成的全部 cases：

- 所有 case 通过 schema 和概率检查；
- case ID 全局唯一；
- 精确输入不存在重复或冲突 gold；
- `group_key` 不跨 split；
- 文件 SHA256 已保存。

构造 manifest 另行记录来源、类型及标签数量，verification 按来源家族和任务家族
统计数量。`original_records` 按 adapter
提供的 `original_id` 去重计数，不代表系统已分别识别原始材料和独立监督单元。

发布前还需按任务补充候选数分布、独立监督数量和派生倍率，并核对最终文件与发布
统计一致。上述自动检查不验证配额是否满足，也不判断标签的语义是否正确。

## 模型输入验收

使用 `prepare` 对实际使用的每个 split 编译后检查：

- 使用训练 bundle 的实际 tokenizer；
- `max_len / head_max_len` 与训练配置一致；
- 候选与问题指令不得截断；
- state 截断策略显式记录；
- 每个 split 的接受量、拒收量和长度分布已保存。

编译结果不会回写原 cases 或构造 manifest。若任务要求完整的多选题选项包，应再
检查拒收是否破坏母题完整性；训练样本量应以最终接受的记录为准。

## 语义验收

- 每个 task family 的标签含义可从原来源追溯；
- 负例具有明确依据；
- 多答案、未知和部分支持等状态没有被压成错误二分类；
- 训练、开发、校准和测试的用途明确；
- 测试材料及同母单位派生记录没有回流训练。

## 发布边界

- 代码许可与数据许可分别记录；
- 数据来源、版本、修改方式和访问限制完整；
- 允许训练不自动等于允许公开再分发；
- 发布说明不把派生 decision 数写成独立原始样本数。
